# 无限记：开发规格与决策稿

日期：2026-11-14。状态：第一阶段原型已编写，原生架构关键边界待用户确认。

## 产品目标

独立品牌“无限记”，在 Windows、Android 手机和 Android 平板提供与 Apple“无边记”相近的无限画板能力，使用液态玻璃风格，并增加自选工作目录、业务热更新、内置中英语音输入和英文 26 键键盘。

“全部功能”作为最终对齐目标，不能用只有绘图的演示页冒充完成。对齐范围应锁定参考版本，按功能矩阵逐项验收。Apple 当前使用手册列出的范围包括看板、文字与媒体、图形、表格与图表、场景、整理、共享协作、删除恢复、PDF 导出等。本版只覆盖其中一部分。

独立实现自己的云服务、身份和协作能力；Apple 账号、iCloud（苹果云服务）、FaceTime（苹果通话服务）等生态能力不直接等同于可移植的画板功能。若需要与 Apple 无边记互传原始文件，必须单独验证公开格式及接口，不能预设兼容。

## 建议的正式架构

### 客户端：固定原生外壳 + 可热更新业务层

建议选择 Tauri 2（跨平台原生外壳框架）配合共享网页业务层；当前原型使用无第三方框架依赖的 JavaScript 模块，后续可按复杂度迁移到 TypeScript（带类型检查的 JavaScript）和 React（界面框架）。不要求用户为架构细节做选择，除非下方关键边界改变。

Tauri 2 支持桌面和移动端。Windows 使用 WebView2（系统网页视图），Android 使用系统 WebView（网页视图）。液态玻璃通过前端绘制，降低透明效果时保留相同交互与可读性。

固定壳必须承担：启动/恢复、权限、目录授权、文件读写桥接、录音、模型原生推理接口、公钥验签、更新激活与回滚、操作系统生命周期。**这些也是本项目自写的代码，不能承诺全部从安装包中去除。** 若“框架之外的代码全部外置”按字面要求连桥接代码都不得安装，需改为允许脚本的极薄壳并接受原生能力受限，且仍无法绕开系统权限和运行库。

可外置部分：界面 HTML/CSS/JavaScript（网页结构/样式/逻辑）、画布业务、素材、主题、词表、语音模型、工作区数据，以及可选的开发源文件副本。开发源文件与运行资源包区分保存，不把未经构建的 TypeScript 当成可直接运行资源。

### 自选文件夹

建议工作目录包含如下子目录：

| 路径 | 用途 |
| --- | --- |
| `runtime/releases/版本号/` | 已验证的业务资源包 |
| `runtime/active.json` | 当前版本指针，交由壳更新器维护 |
| `workspace/boards/` | 看板数据及可恢复的变更记录 |
| `workspace/assets/` | 图片、音频等素材 |
| `models/` | 模型、分词/词表文件及校验清单 |
| `config/` | 用户外观、输入和目录配置；不含明文密钥 |
| `backups/` | 可回滚的数据与版本备份 |
| `source/` | 可选的可编辑源文件副本 |

Android 应使用 Storage Access Framework（存储访问框架）选择目录，并持久保存授权 URI（资源标识）。不是任意路径字符串；部分系统目录不可选。若用户移动目录、撤销授权或拔出存储卡，必须进入恢复页，允许重新选目录，不能静默新建空工作区后覆盖云端。

为性能和权限稳定，建议允许将已验签版本复制到应用私有缓存再运行，用户目录仍保留业务包和数据。若要求只从用户目录运行、禁止任何私有缓存，需先在目标 Android 设备验证自定义资源协议、目录提供者读取性能和启动稳定性。

### 热更新能力边界

| 变更 | 目标更新方式 |
| --- | --- |
| 样式、布局、画布业务逻辑、词表、素材 | 签名资源包热更新 |
| 原生推理接口兼容的语音模型 | 独立模型下载与校验，通常可免重装 |
| 业务数据结构 | 带版本迁移、先备份再升级 |
| 新权限、系统输入法服务、原生推理运行库、系统桥接接口 | 需要原生壳升级；Android 仍可能要更新 APK |

Tauri 官方 updater（整包更新插件）不支持 Android，并不能直接满足本项目的业务热更新需求。应另建业务资源包更新器；Windows 壳更新和 Android 壳更新另外处理。

完整更新流程应为：获取签名清单 → 检查壳接口最低版本和发布序号 → 下载临时目录 → 校验清单签名及所有资源摘要 → 解包到版本目录 → 原子切换活动指针 → 首次启动健康检查 → 成功后确认版本；失败自动回到上一业务版本。数据迁移必须可恢复，不能只回退界面却让旧版本读取已破坏的数据。

当前 `tools/release.py` 只落实签名包与验证/发布环节，未实现这条客户端闭环。允许在开发模式下加载本地编辑版本的需求，也需单独配置；正式模式不自动执行任意未经签名的外部目录代码。

### 输入法与语音

默认建议为“应用内输入面板”，只在无限记自己的文字编辑框生效。系统级输入法是另一项原生工程：Android 需要 InputMethodService（输入法服务）；Windows 需要独立的系统文本输入集成。启用系统输入法需用户在系统设置中主动选择。

建议正式版使用 sherpa-onnx（离线语音推理工具）和现成的中英双语流式模型，先对普通话、英语及混说场景做真机测试；可比较轻量模型的速度、精度、内存及耗电。不能只凭桌面演示承诺手机实时识别效果。每个选定模型需确认自己的许可证、来源和文件摘要，推理工具的许可证不代表所有模型的许可证。

模型按需下载到 `models/`，首次启用时显示实际大小，允许离线导入。默认不上传录音。中文需求当前理解为普通话；粤语等方言另行说明。

### 服务端

当前为 Python 标准库 + SQLite 的个人原型，方便低成本本机启动。正式服务建议将职责分成账号与访问控制、看板元数据/版本、媒体对象存储、协作会话、签名更新分发、备份恢复。具体数据库和部署方案按服务器条件选择，不预先绑定付费供应商。

多人实时协作建议采用 CRDT（无冲突复制数据类型）类同步方案，按对象和属性合并；不要把整张看板“最后写入覆盖”当成实时协作。断网编辑、恢复联网、两设备同时移动同一对象、删除与修改冲突、权限撤回、附件断点重传都要独立验收。

公开多用户服务必须实现账号隔离和共享权限，不能沿用本原型的全工作区共享密钥。访问密钥、登录令牌等保存在系统凭据存储中；如果选择端到端加密（只有用户设备可解密），须同时设计恢复密钥、设备加入和共享方案。

## 后续里程碑与完成标准

1. **原生外壳与存储闭环**：至少一台 Windows、一部 Android 手机、一台 Android 平板安装启动；首次目录授权、应用重启、设备重启、授权失效恢复；离线保存与导出恢复；适配触屏/鼠标。
2. **热更新闭环**：安装旧壳，从服务下载新业务包；验证界面/逻辑变化，无需重装 APK；修改包被拒绝；断网/断电/首启失败自动恢复；数据迁移失败不损失工作区。
3. **输入闭环**：应用内 QWERTY 键盘能稳定编辑；按确认的方式接入真实中英语音引擎，在目标设备测试；取消后停止录音，禁用时不申请麦克风。
4. **完整画板对齐**：补齐多选/分组/对齐/吸附、连接线、富文本、媒体预览、场景展示、文件夹和回收站、PDF 导出等，逐项记录参考行为和差异。
5. **云端与协作**：账号隔离、媒体存储、备份恢复；按首版决策加入实时协作、共享权限与冲突合并；验证跨设备离线恢复和撤权。
6. **发布验收**：Windows 安装包和已签名 APK；手机/平板横竖屏、笔输入、低内存、升级恢复、访问性与实际用户流程通过。

建议的大看板性能目标先作为待测指标，不在没有实测时承诺：以目标设备测试 1 千/1 万对象，记录拖动帧率、首开耗时和峰值内存，再决定虚拟化、图形渲染和资源缓存方案。当前 SVG 渲染只是基础实现。
